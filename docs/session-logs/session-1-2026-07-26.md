# Session 1 — 2026-07-26

## Goal

`glyphrogue/BACKLOG.md`'s session-42 close-out pointed the next session at
scoping a downstream test game — the first real consumer of
`create-glyphrogue-game` — rather than more engine work. This was that
session, run as a `/decision-session`: a from-scratch discovery
conversation, real decisions resolved live one at a time, four separate
cohesion audits along the way, ending in a complete `DESIGN.md` and a new
`glyphkeep` project.

## Key decisions

- **Ambition**: a small, genuinely playable roguelike that also touches as
  much of `glyphrogue`'s feature surface as possible — not a pure smoke
  test, not a narrow demo. This shaped every decision after it toward
  "yes, and how do we make it fit" rather than cutting for scope.
- **Theme**: a haunted ruin of "the keep," with Duke Glyphmund's fallen
  family (all ghosts) each bound to a different mechanic — Glyphelda to
  shrines/the essence economy, Glyphrey to the shop/loadout/shard-
  identification economy, Glyphard to curses/hazards/teleporters. This
  turned out to be the single biggest cohesion win of the session: nearly
  every previously mechanical-but-faceless system (shrines, shops, curses)
  ended up with a character behind it.
- **Structure**: static floor-0 hub (loadout, essence shrine, Trophy Case,
  Artifact Cabinet) → 10 runtime-generated floors, one-way descent → Duke
  Glyphmund on floor 10.
- **Four progression axes**: essence (permanent, frequent), gold (in-run,
  shops), boons/relics (in-run, shrine-exclusive), artifact shards (rare,
  in-run until identified by Glyphrey for a gold cost — a genuine
  identify-vs-gear-up tension). Achievements sit alongside as a fifth,
  progression-adjacent system.
- **Resolving `glyphrogue/.claude/tokenote-notes.md`'s open meta-
  progression item** was explicit new scope, not incidental — see "Work
  completed" below.
- **New Game+** was added late in the session at the user's explicit
  request, specifically for replay value, becoming its own final
  implementation phase.
- **Combat had to be designed from scratch** — `glyphrogue/packages/core`
  provides no built-in combat system, only the generic action/rule
  dispatch pipeline. Bump-to-attack, accuracy/evasion + damage rolls
  against the seeded RNG, Health/Attack/Defense stats, melee-only through
  the early phases.
- **Cross-project workflow for `glyphrogue` issues found during
  implementation**: log immediately, fix small/unambiguous gaps the same
  session directly in `glyphrogue` (matching every prior downstream-
  consumer session's precedent), batch bigger ones for their own design
  conversation, use `npm link` while iterating rather than a publish cycle
  per fix, publish for real only at natural checkpoints. Landed in the new
  `glyphkeep/.claude/dev-session.md`.

## How the session actually ran

Four separate cohesion/gap audits, each catching real, load-bearing
issues rather than nitpicks — a genuine argument for asking for more than
one when scope is growing fast:

1. An `Explore`-agent audit of `glyphrogue`'s own docs/BACKLOG/export
   surface surfaced four additions the design hadn't touched yet:
   scripted events + the dialogue screen, logical links/teleporters,
   gamepad support, and the achievement hook — plus flagged player-facing
   mod support as needing new engine work, kept backlogged instead.
2. A cohesion pass over the design-so-far found: the boss and the
   standalone `Guards` enemy needed to be distinct; shops and shrines
   needed separate currencies (gold vs. essence) or the "permanent" bank
   would leak; the settings screen needed to be real (not folded into
   pause) once a colorblind toggle needed a home; achievements needed
   their own tracking since the platform hook no-ops on a plain web build;
   boons needed a display surface; boons needed a source (shrines).
3. A third pass caught that no-backtracking had never actually been
   decided despite "descend" framing everywhere, and that torches/keys —
   mentioned in the very first "rough shape" answer — had never been
   revisited, leaving "vaults" as the one event-room type with no real
   mechanic.
4. A final pass (after New Game+ and the family/artifact system were
   layered in) checked for fallout from all the additions and found the
   death/run-summary screen's scope had gone stale, and confirmed the
   Trophy Case/Artifact Cabinet's hub-only access was worth widening to
   pause-menu access too.

Also mid-session: the user proposed tying essence-spending to a floor-0
Glyphelda shrine, which doubled as her narrative introduction — not
something the audits found, a user-driven cohesion improvement that gave
Glyphelda a hub presence symmetric to Glyphrey's.

## GitHub / Pages

`gh` CLI is not installed in this environment (checked both git-bash and
PowerShell), so the GitHub remote and Pages source setting couldn't be
configured programmatically — handed off to the user instead. They
created [Rhapsydian/glyphkeep](https://github.com/Rhapsydian/glyphkeep)
(public, no auto-init) and set Pages' source to GitHub Actions manually.
The assistant verified the empty remote was reachable (`git ls-remote`),
then added it as `origin` and pushed `main` after an explicit go-ahead.
Nothing is actually playable on Pages yet — this session's push is the
design doc only; Pages activates once Phase 1 adds the scaffold's
`deploy-pages.yml` workflow and pushes.

## Notes

This was the first `/decision-session` used for a from-scratch project
rather than an in-progress design gap — situation #2 in the skill's three
covered cases. No pre-existing gap list existed going in; the whole
concept (theme, family cast, all four progression axes, New Game+) was
built up live over many rounds rather than filled in against a known
checklist. The user explicitly asked for repeated audit passes rather than
treating the first "looks done" moment as final, and each pass found
something real — a good signal that for a project this size, more than
one audit pass earns its keep.
