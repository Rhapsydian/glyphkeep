## Key decisions

- **Scaffold vs. existing repo**, resolved live via `AskUserQuestion`:
  `npm create glyphrogue-game`'s `targetDirIsUsable` refuses a non-empty
  target, and this repo already had `DESIGN.md`/`BACKLOG.md`/`README.md`/
  `.claude/`/`docs/`/git history. Scaffolded to a scratch dir with the
  real CLI, then copied the generated files in by hand, leaving existing
  docs untouched.
- **Floor 0 (the hub) is out of scope for Phase 1** — `DESIGN.md`'s phase
  list never mentions it for phase 1; Glyphrey's loadout is phase 3,
  Glyphelda's shrine is phase 4, Trophy Case/Artifact Cabinet are phase
  6. Phase 1 starts the player directly on floor 1.
- **A custom BSP floor generator, not the stock `bspPlugin`** — the stock
  `bspGenerator` discards `carveBsp`'s `rooms` list once the zone is
  built, so there was no way to place a stairs anchor in a specific room
  (the one farthest from entry) through it. `src/generators/
  floorGenerator.js` calls `carveBsp` directly instead.
- **Floor-sequencing is entirely glyphkeep-owned state** (`src/floor.js`)
  — `glyphrogue` has no "current zone" concept anywhere (the same gap
  that's blocked the map editor's in-context editing since session 34),
  but a `Zone` is just a DTO `api.generateZone` returns, so holding
  "which floor we're on" needs no engine support at all.
- **Combat needed its own seeded rng stream** — a rule's `ctx`
  (`actions.js`) has no rng access at all, only a *generator*'s ctx does.
  Real architectural gap, not fixed live (see "Cross-project fixes"
  below) — worked around with `createRng(api.rng.state)` in
  `src/rules.js`.
- **A new standing process, requested live at close of Phase 1**: at the
  end of every implementation phase, review completed work for
  `glyphrogue` plugin/baseline candidates and recommend whether a
  dedicated `glyphrogue` session (and a glyphkeep fold-back session)
  should happen before the next phase; and when a session makes real
  `glyphrogue` changes, write a session log in both repos at close-out,
  not just glyphkeep's (this session log's `glyphrogue`-side sibling is
  `glyphrogue/docs/session-logs/session-43-2026-07-26.md`). Landed in
  `.claude/dev-session.md`.

## Work completed

Four checkpoints, each independently verified in the browser (`dev.html`
and `index.html`) and committed separately, per the `checkpoint-plan`
skill:

   the real scaffold in; replaced its static-template `renderZone` with
   a live loop tying `createCamera`/`updateCamera`, `computeFov`/
   `classifyVisibility`-gated terrain, and real `api.query()`-driven
   entity draw commands together — the first time anyone has assembled
   these `glyphrogue` primitives into a working camera-follows-player
   loop. `package.json` linked against the local `glyphrogue` checkout
   via `file:` references. 8 tests.
2. **Keyboard input wired to movement** (`c7ceaf6`). `src/rules.js`'s
   `Move` rule (walkability + bump-to-attack redirect) and `src/
   input.js`'s keymap/`createKeyboardSource`/`createInputPipeline`
   wiring — `@glyphrogue/input`'s first real gameplay consumer anywhere.
   Also fixed a gap checkpoint 1 left latent (never calling
   `api.addActor` for the player, harmless until this checkpoint started
   calling `run()`). 8 new tests (16 total).
3. **BSP floors 1-10, descent, trivial win** (`4a285da`). Custom floor
   generator with a stairs anchor in the farthest room; `src/floor.js`
   owns descent/regeneration with tag-based entity cleanup (self-healing
   against `dev-main.js`'s HMR restore path, where `floor.js`'s own
   JS-closure state doesn't survive a reload but the restored world's
   entities do); a placeholder win overlay on floor 10. 10 new tests (26
   total).
4. **`Wanders` enemy, combat, permadeath** (`5312f9e`). One
   `Wanders`-behavior enemy per room (`src/plugins/enemy-plugin`, reusing
   `glyphrogue`'s real `wandersPlugin`); `Attack`/`Die` rules; permadeath
   to a placeholder death screen, with `dieRule` deliberately leaving a
   defeated *player* entity alone (destroying it would erase the `Health`
   state the outer game loop needs to detect death after `dispatch`
   already resolved synchronously). 7 new tests (33 total, all green
   throughout).

Verified end-to-end in the browser at every checkpoint via real
`KeyboardEvent`s (wall-blocked movement, a full 10-floor playthrough via
stairs, real bump-to-attack combat killing a wanderer in one hit, forced
permadeath through the same code path a real lethal hit takes) — zero
console errors throughout.

## Cross-project fixes

Per `.claude/dev-session.md`'s convention, small/unambiguous gaps found
along the way were fixed live, directly in `glyphrogue`, with regression

  `glyphrogue`'s own Tokenote companion notes.

  `.gitignore` (same commit, same Tokenote source) — glyphkeep's own
  root `.gitignore` was added by hand in checkpoint 1 and never fed back.

One bigger gap was logged but deliberately **not** fixed this session — a
rule's `ctx` has no rng access at all, a real architectural change
(`actions.js`/`engine.js`/`api.js`), not a small export fix. It's now
`glyphrogue/BACKLOG.md`'s NEXT SESSION pointer. See the "Phase-end
review" section below for the full picture, including three more
candidates surfaced for later (not gaps to fix, but glyphkeep-authored

## Phase-end review

Requested live at Phase 1's close: review completed work for `glyphrogue`
plugin/baseline candidates. Full writeup is in the conversation and now
in both `BACKLOG.md`s; summary:

- **Strong candidate**: move-action resolution as a first-party Content
  plugin — every shipped AI behavior emits `Move` follow-ons that nothing
  in `glyphrogue` resolves. glyphkeep's `moveRule` is a working
  reference; its bump-to-attack policy specifically is more game-specific
  and probably shouldn't come along for the ride.
- **Moderate, wait for more evidence**: the camera/FOV/render-loop
  assembly and the keyboard-input wiring are both genuine firsts (no
  consumer had ever assembled either before) and plausible
  scaffold-template material, but deliberately left for Phase 2 to
  provide a second data point before locking in a shape.
- **Correctly stays glyphkeep-only**: the combat system itself (`DESIGN.md`
  and `glyphrogue`'s own docs are already deliberate that combat is out
  of engine scope).

All three "wait" candidates and the strong candidate are now recorded in
`glyphrogue/BACKLOG.md`'s "Deferred / future items", each tagged to
revisit once glyphkeep's Phase 2 exists.
