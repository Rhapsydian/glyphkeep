## Key decisions

- **Package linkage needed no changes.** `package.json`'s
  `@glyphrogue/core` dependency is a `file:` reference resolving to a real
  symlink into the sibling `glyphrogue` checkout, with no build step
  (`exports: { ".": "./src/index.js" }`) — the just-landed `ctx.rng`/
  `isWalkableCell` changes were already live in `node_modules` the moment
  the `glyphrogue` session committed them. Confirmed directly rather than
  assumed, since a stale link would have silently made this session's
  changes fail at runtime.
- **`cellAt` stays, not part of the swap.** `game.js`'s
  `classifyTerrainCell` needs the raw cell-type string for rendering (wall
  vs. floor tile lookup), not a walkable boolean — only
  `isWalkableInZone`/`isOpaqueInZone` got reimplemented in terms of
  `isWalkableCell`, keeping their existing exported names so every call
  site (`main.js`, `dev-main.js`, `game.js`'s own renderer) stayed
  unchanged.
- **`isOpaqueInZone(zone, x, y) = !isWalkableCell(zone, x, y)`** — flagged
  as a coincidence, not a real equivalence: walkable and opaque are
  different properties that just happen to collapse to the same check
  today because every zone glyphkeep generates has exactly two cell
  values (`'wall'`/`'floor'`), confirmed by grepping all of `src/` and
  `@glyphrogue/core`'s own BSP/zone pipeline — no `'door'` or other third
  cell type exists anywhere yet. Documented in a comment at the
  definition site and in `BACKLOG.md`'s NEXT SESSION note, so Phase 5's
  stamped event rooms (the first place this is expected to actually
  matter) don't have to rediscover it.
- **Combat rolls don't visibly change today, but the reasoning is
  forward-looking.** `combatRng` was seeded from `api.rng.state` at the
  exact moment of bootstrap, before anything else had touched
  `api.rng.next()` (zone generation uses its own hash-derived per-zone
  stream, never `api.rng` directly) — so `combatRng`'s old sequence and
  the new shared `ctx.rng`'s sequence are identical in every existing
  scenario. The real behavior change is future: once some other system
  (a Phase 2 behavior needing its own roll, say) draws from the shared
  stream before combat does, combat's sequence will diverge from what the
  old frozen-copy workaround would have produced. Noted here so a future
  session doesn't mistake that divergence for a regression.
